# 个人消费账单合并与消费画像分析

> **定位**：业务需求分析与规格设计（Business Requirements Analysis & Specification Design）
> **对标岗位**：ANZSCO 261111 ICT Business Analyst / 261112 Systems Analyst
> **技术栈**：MySQL 8.0（三源异构数据合并、口径建模、可审计分析）
> **数据范围**：2026-03-29 ~ 2026-09-29 真实个人账单，6 个月，623 条原始记录

---

## 为什么做这个项目

宿舍清空的时候发现买了一堆没用的东西，每月都有说不清去向的钱 —— 生活费本来就不多，想让财务状况更健康。

所以这不是「统计花了多少」，是**先把「什么算消费」定义清楚，再找出哪些钱是白花的**，好让下个月的预算有个可信的基数。这个目标直接决定了口径取舍：钱实实在在出去的（红包、请客）必须算进来；钱只是换了个口袋的（卡间划转、提现）必须剔掉。

---

## 这个项目在做什么

三份来自不同渠道的账单（微信、支付宝、工商银行）**不能直接相加**：

- 同一笔钱可能被**记两次**（跨源重复）—— 不去重，总支出虚高 **24.62%**
- 「转账」两个字下面混着**三种性质完全不同**的钱 —— 一刀切剔除会凭空抹掉 ¥941 真实开销
- 有些消费**只以数字形式可见**（银行侧只有「消费/快捷支付」四个字）—— 能证明钱少了，不能证明钱花在哪

**我做的不是「统计」，是先把「什么算消费」这件事定义清楚，再让每个数字都能被第三方复核。**

> ⚠ 上一版示例数据是「拿真实账单改的」：只把商户名替换成"示例XX"，日期、时间、金额、
> 余额链原样保留。实测与真实账单的重合率 —— **工行 94%、支付宝 55%**。
> **换个商户名不等于脱敏**：时间 + 金额的组合本身就足以定位到具体交易。已全部重造。

## 快速开始

> **前置**：先确认 MySQL 的 `secure_file_priv` 白名单目录。
> 用 `SHOW VARIABLES LIKE 'secure_file_priv';` 查询，把 CSV 放进去。
> 本项目脚本内的路径为 `F:/allstudy/mysql/data/Uploads/`，**请按自己的实际路径修改 `账单导入.sql`**。

### 1. 建表

```bash
mysql -u root -p --default-character-set=utf8mb4 < 账单建表.sql
```

### 2. 导入数据

把 `示例数据/` 下的三个示例 CSV **改名为脚本约定的文件名**，复制到白名单目录：

| 示例文件 | 复制为 |
|---|---|
| `示例数据/微信支付账单_示例.csv` | `<白名单目录>/bill_wechat.csv` |
| `示例数据/支付宝交易明细_示例.csv` | `<白名单目录>/bill_alipay.csv` |
| `示例数据/工商银行历史明细_示例.csv` | `<白名单目录>/bill_icbc.csv` |

然后执行：

```bash
mysql -u root -p --default-character-set=utf8mb4 < 账单导入.sql
```

> **注意**：示例 CSV 已按 `账单导入.sql` 的要求保存为 **CRLF 行结束符**，
> 若你用编辑器另存过，请确保行结束符仍为 CRLF，否则会导入 0 行。

### 3. 合并为统一口径

```bash
mysql -u root -p --default-character-set=utf8mb4 < 账单合并总表.sql
```

### 4. 跑分析

```bash
mysql -u root -p --default-character-set=utf8mb4 < 账单分析查询.sql
```

Windows 用户也可双击 `账单分析.cmd` 进入交互式工作台。

> **示例数据的验证结果**（2026-10-12 实测跑通，非估算）：
>
> | 环节 | 结果 |
> |---|---|
> | 导入 | **133 笔**（微信 67 / 支付宝 20 / 工行 46） |
> | 工行侧非支出行排除 | 11 笔（9 笔「微信零钱提现」+ 2 笔「退款」，均为正数进账） |
> | 跨源去重命中 | **19 笔**（工行 35 笔支出 → 16 笔） |
> | `v_bill`（全部支出口径） | **103 笔 / ¥4,338.06** |
> | 转账细分 | 人情往来 9 笔 ¥490.35（计入）· 资金搬运 3 笔 ¥554.20（剔除） |
> | 一次性大额标记 | 15 笔 |
>
> 去重、退款、一次性大额、转账细分四条判定全部命中，**流程完整可复现**。
> 数字与真实数据不同属正常 —— 示例数据是独立生成的虚构样本。

## 核心口径（三层）

| 口径层 | 视图 | 定义 | 笔数 | 金额 |
|---|---|---|---|---|
| **L1 全部支出** | `v_bill` | 三源合并后，剔除退款（含工行回流）+ 剔除跨源重复 | 602 | ¥23,104.78 |
| **L2 高频小额消费** | `v_bill` + `is_oneoff=0` | 剔除全部转账与标记类目（学费/医疗/驾校等） | 551 | ¥7,923.55 |
| **L3 真实消费** | `v_spend` | **分叉判定**（不是层层相减）：转账类只留「人情往来」，非转账类剔一次性大额 | 570 | ¥8,864.69 |

## 三个关键判断（也是这个项目的核心价值）

### 判断一：跨源去重必须做，但判据本身会失效

**重复记账的真实构成**（逐笔核对支付方式列得出）：

| 路径 | 笔数 | 金额 |
|---|---|---|
| 支付宝绑工行卡快捷支付 | **17 笔** | ¥113.42 |
| 微信扫码/商户消费用工行卡 | 2 笔 | ¥5,520.00 |
| 合计（`is_dup`） | **19 笔** | ¥5,633.42 |

**但有一类记录「长得像重复，却绝不能剔」**：微信「零钱提现」两边都有记录，然而
① 微信侧 `in_out='/'` 从未进支出统计 ② 工行侧是**正数进账** ③ 两边金额差 **0.1% 提现手续费**。
→ **判重必须看语义（是否同一笔支出被算两次），不能看形态（是否两边都有记录）。**

**判据的失效**：v1 用「时间完全相等」，实测漏判 14 笔（支付宝走工行卡 18 笔只抓到 4 笔）。
根因是渠道落账有 0~16 秒延迟。**这不是技术 bug，是需求定义错误** —— 没人先问过「延迟允许多少」。
改为 60 秒容差后命中 5 → 19 笔。
**残余风险**：60 秒是我单方面定的安全边界，不是业务裁决，**容差取多少该由业务方拍板**。

### 判断二：转账不能一刀切

| 细分 | 笔数 | 金额 | 处置 |
|---|---|---|---|
| 资金搬运（卡间划转/提现） | 13 | ¥2,688.00 | ❌ 不算消费 |
| 人情往来（红包/送礼/请客） | 19 | ¥941.14 | ✅ **算消费** |
| 零星对账（<¥1） | 1 | ¥0.10 | △ 噪声单列 |

### 判断三：分不清就承认分不清

曾用「金额有无零头」猜 AA 分账 → 只捞到 1 笔，自相矛盾。
曾把人情往来整体剔除 → 抹掉 ¥941.14 真实开销。
**最终原则：数据无可靠特征时，诚实归类 + 写明局限，不伪造精度。**
（转账细分规则迭代了 3 版，错误版本保留在 SQL 注释里）

## 数据可见性边界（这个项目真正的天花板）

工行「消费 快捷支付」共 **39 笔**，其中 **22 笔找不到任何来源** ——
钱在银行侧扣了，但**平台不提供账单导出**。

**2026-10-12 实证补充**：两年期工行 PDF 新增「对方户名」列后，这批记录主因查清 ——
**拼多多系 91 笔 ¥1,412.40，占工行消费笔数 44%**（抖音仅 3 笔 ¥11.57）。

> **⚠ 勘误**：本文件 v1.2 曾写「经核实是抖音等 App 内的消费」—— 那是**在没有证据时凭印象填的空**（当时工行 CSV 无对方户名列）。
> 实测主因是拼多多，量级差 30 倍。错误版本保留在此：**无证据时不得在规格里写具体归因。**

必须区分三类"缺口"，性质完全不同：

| 类型 | 实例 | 性质 |
|---|---|---|
| **未发生** | 支付宝缺 2026-08（当月微信 87 笔、工行 3 笔） | **不是缺失**，是真实的行为分布 |
| **发生了但取不到** | 工行 22 笔（**拼多多系为主**，无导出入口） | **真缺失**，且在平台侧 |
| **无法区分以上两者** | 在表里**都是「0 条 / 无匹配」** | **规格缺陷** |

→ **银行流水是唯一「全量」视角，却是信息最贫瘠的视角**：只有 `消费 / 快捷支付` 几个字，
**能证明「钱少了」，不能证明「钱花在哪」。**

→ 这才是「放量到 100 人先崩哪一步」的答案：不是规则不准，是**数据可见性**。
而它**无法靠数据自身发现**，只能靠业务方的外部知识 —— **这是需求规格的活，不是 SQL 的活**。

完整分析见 `04_需求规格说明书.md` §12。

## 已知局限（不隐藏）

1. **跨源去重有双向误差**：~~漏判已实测发生（v2 仍剩 1 笔）~~；误伤是放宽阈值的必然代价。**阈值取多少待业务方拍板**。  
   **2026-11-14 订正**：半年窗口内 17 笔应剔、17 笔全中（原「剩 1 笔」是退款记录，不是支出）；但跨窗口回看，那笔扣款延迟 **179 秒**，确实超容差，只是发生在半年窗口之前。
   **两年期回验（2026-10-12）**：60 秒覆盖率仅 **92%**，需 300 秒才 100%，最大实测延迟 **179 秒**（详见 `05_两年期数据体检.md`）
2. 工行侧无商户名，跨源商户排行有粒度差异
3. 19 笔「人情往来」中可能含少量 AA 垫款，数据无特征可辨
4. 「其他消费」占比 17.7%（¥1,579.54），分类关键词仍需迭代
5. 2026-03 为残缺月（数据从 3-29 开始），不与完整月对比
6. 单人单期数据，不产生人群或年度结论
7. **工行侧「已退款」不回流（已修，2026-11-14）**：微信改写状态、支付宝新增退款行，工行只新增一笔正数流水，
   原扣款行原样保留 → 半年窗口里 3 笔 ¥85.70（占 L3 的 0.96%），两年窗口 51 笔 ¥1,550.79（2.92%）。
   已按「同额 + 30 天内 + 取时间差最近的 N 笔」配对剔除 **39 笔 ¥1,407.89**，两年 L3 ¥53,115.71 → **¥51,707.82**；
   余 **10 笔 ¥107.01**（间隔超 30 天）**不认，记为未解释差异**。详见 `04_需求规格说明书.md` §8.3
8. **所有规则都是样本拟合的产物** —— 放量到 100 人会成片失效
9. **数据可见性受限** —— 工行「消费」类 206 笔中仅 54 笔有源，152 笔 ¥2,167.49 找不到（实证主因拼多多系 90 笔）；且「未发生」与「取不到」在数据里无法区分
